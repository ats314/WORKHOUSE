# Registers and their roles

| File | Contents | Standing |
|---|---|---|
| `governing_register.yaml` | R1–R23, verbatim from the governing document §14 | **authority** |
| `contradictions.yaml` | C1–C22, from `MASTER_THEORY.md` §8 | historical numbering, kept because checks cite it |
| `gaps.yaml` | registered G-ids and `unifying_candidates` | the open-work register |
| `results.yaml` | stable `RESULT:` claims with hypotheses and proof sources | analytic results and their explicitly scoped evidence |
| `documents.yaml` | native `CITE:` aliases, source paths and documentary connections | source identity and provenance |
| `derivation_statements.yaml` | located `DERIV:` statement groups, hypotheses, dependencies and remaining work | source status and explicitly scoped formal coverage |
| `theorems.yaml` | every registered Lean theorem, including helpers | authored theorem-to-source scope and exact-check promotions |
| `lean_dependencies.json` | elaborated Lean declaration dependencies and transitive axioms | generated by the strict exporter; never edit by hand |
| `recent_research.yaml` | preserved campaign sources and authored result/route records | source hashes and scoped integration of recent research |
| `notes.yaml` | archive inventories and content-digest review verdicts | intake and review status, without implicit certification |

Where the R and C transcriptions differ, R governs the documentary crosswalk.

The governing register is a documentary transcription, not a substitute for
later derivations. Current resolutions and research consequences live in the
contradiction, gap and result registers. Keep each source's historical wording
and record why the mathematical status changed.

`results.yaml` separates a theorem from the file that contains it. Use the
existing status and evidence vocabularies; an analytic proof can be `proven`
while its full statement remains T3 for machine certification. Each result
names its exact hypotheses, scope, pinned `CITE:` source and source section.
`depends_on` records mathematical inputs; `bears_on` records consequences or
relevance. `supported_by` records controls with an explicit statement of what
they check. A finite control is not an implicit proof of the larger claim.
The generator validates source pins and graph endpoints and rejects cyclic
result dependencies.

Routes may cite registered `RESULT:`, resolved `CITE:` or `LEAN:` closers and
declare `depends_on` inputs. Naming an existing closer is a structural check;
review its mathematical scope before marking a route done. After changing
source ledgers, validate the relevant register, regenerate affected views and
query the result and gap with `workhouse why`. Update the current research map
and land green work under the root [working agreement](../CLAUDE.md).

Curated crosslink files follow the same discipline (judgement in the YAML,
the join derived, validation mechanical): `symbols.yaml` maps repo
names to corpus spellings, `theorems.yaml` maps each Lean theorem to the
claims it `formalizes` and the checks it `promotes`, and `provenance.yaml`
names the corpus documents that *originate* values — originators, never
carriers, because repetition is not independence. `tests/test_graph.py`
rejects an entry whose name, formalizes target, or promotes check does not
resolve — a promotes check must resolve to exactly one registered check — and
`tests/test_provenance.py` rejects a provenance entry whose file does not hash
to its corpus pin, whose quote is not found near its recorded line, or whose
target does not resolve.

The `notes.yaml` register tracks the maintainer's own note archives
under review — verdicts keyed by content digest, every verdict with a reason,
imports byte-verified. `src/workhouse/notes.py` enforces it and
`notes/README.md` explains the flow.

## Located derivations and kernel dependencies

Follow the [formalization workflow](../docs/formalization_workflow.md) and use
the generated [proof map](../docs/derivation_formalization.md) for live counts.
Do not copy coverage totals into agent rules.

Each document in `derivation_statements.yaml` has its existing native `CITE:`
alias, exact path and raw-byte SHA-256. Its statement groups have stable
`DERIV:` IDs, a locator and anchor in the received text, explicit hypotheses,
source-level `depends_on` IDs and a `remaining` obligation. Source status and
evidence use the existing closed vocabularies independently of formal coverage.
The inventory validator checks every top-level derivation document, source
hashes and anchors, theorem-name resolution and dependency cycles.

Use `lean` only for a proof of the entire named statement. Partial ingredients
belong in `lean_support` with an exact `scope`. These generate different graph
edges: `LEAN -> DERIV formalizes` and `DERIV -> LEAN supported_by`. The source
statement remains T3; a linked Lean theorem has its own T0 certificate. A hash
match proves source identity, and a compiled helper proves its own conclusion;
neither alone establishes full source coverage.

Register every new theorem, including helpers, before running
`python scripts/export_lean_dependencies.py`. It performs the strict Lean build
and writes `lean_dependencies.json` from elaborated constants. The loader checks
registered names, allowed transitive axioms, project dependency extraction and
source fingerprints. It traverses local definitions until the next registered
theorem. Do not replace this record with a source-text keyword scan or edit it
by hand. Its `utf8-lf` fingerprints tolerate checkout line endings; derivation
and sealed-evidence hashes retain the original bytes.

Then refresh `docs/derivation_formalization.md` with its renderer and regenerate
the catalogue, frontier and certification views in order. Read the resulting
`workhouse why DERIV:...` and `workhouse why LEAN:...` output to confirm both
source scope and actual proof dependencies.

## Do not hand-edit governing_register.yaml

It is generated by `scripts/transcribe_register.py`, and `text` is verbatim.
`tests/test_ledger.py` re-extracts §14 and compares, so a paraphrase is a build
failure. That is deliberate: a register retold once per version drifts one
defensible rewording at a time, and each step looks fine on its own.

Only `CROSSWALK` in that script is authored by hand. Add a pair there **only**
when the register item and the C-id state the *same* claim, not a related one.
The transcription tests pin this crosswalk, so changes need a source-based
explanation.

## Rules validate() enforces

- id sequences complete, no gaps
- statuses inside the closed vocabularies
- every cross-reference resolves
- an open contradiction must name a gap that would resolve it, and some gap must
  claim to resolve it — an open item nobody is working on is how a register rots
- every `unifying_candidate` carries a **falsifier**. A candidate without one is
  an analogy, and analogies accumulate without ever being wrong.

Preserve old evidence and concurrent edits. For a change only to this guide,
use [documentation maintenance](../docs/documentation_maintenance.md); do not
rewrite ledgers, source hashes or generated views to tidy their presentation.
